# MODS.md — mods, tweaks, and what stays the base engine

Status: **design agreed 2026-11-04; §8.1's overlay, canonical/DLC mods and their uuids (§14), and the first tweaks are built** (§12), the rest is not. People are forking OpenSWOS to add
what they want, and that is good, but the project cannot merge every fork. A mod system lets
those features exist without being merged, so the engine has to become flexible enough to
host them. This file records the decisions, the survey they came from, and the plan.

---

## 1. Decisions (the owner, 2026-11-04)

1. **The line:** what makes the engine *able to do more* is the **base**; what makes the game
   *different* is a **mod**. There are exceptions (§4, tweaks).
2. **PR #11** (petarku, HISTORIC TOURNAMENTS): the PC/SWOS 2020 `.DIY` reader and the
   competition-load speedup go into the base; HISTORIC TOURNAMENTS becomes the first content mod.
3. **CPU cards** ("the computer gets cards too") goes into the base as a tweak: two forks built
   it independently (petarku, benefactorr).
4. **Code mods** start as source mods compiled in, **with Lua script support at the same time**.
5. **World 2026-27 becomes a mod**, once the overlay and registries exist.
6. **The pitch format is base** (§6): Tile Agent's maps, made with Tile Agent, with a binary
   form the Amiga reads.
7. **Tweaks:** behaviour that differs from the original but is not a mod -- small fixes of the
   original's annoyances -- in `[tweaks]` of SWOS.ini, off by default (§4).
8. **The original is always buildable:** every divergence from the Amiga game sits behind a
   preprocessor switch (§5), and the Amiga gets an **OCS/ECS target** with the original
   graphics beside the AGA one (§7).

We call them **mods**: the word the SWOS scene already uses (the SWOS 96/97 Mod, "modding").
A SWOS 2020 "DLC pack" is a mod you download.

## 3. What is base and what is a mod

**Base:** the original game, faithful to the Amiga and DOS releases (the replay rig and the
golden careers prove it); platforms and infrastructure (ports, netplay, saves, replays, the
setup); reading formats (PC `.DIY`, SWOS 2020's files, Tile Agent maps); the capabilities mods
need (§8); bug fixes and speedups; tweaks (§4).

**Mods:** new modes (indoor, practice, challenges), rule and balance changes, new career
systems (ageing, AI transfers), and content: competitions, worlds, team data, pitches, kits,
graphics, music, commentary, translations.

PR #11 split this way: the `.DIY` reader, the load speedup (petarku offered it as its own PR:
take it first) and the Amiga's folder listing / data-root loading are base; HISTORIC
TOURNAMENTS -- SWOS 2020's cups, which Insane has agreed may be redistributed, with a manifest
-- is the first content mod, shown by a generic "competitions from mods" row in PRESET
COMPETITION so no mod edits `teams.c` or `menu_data.c` again.

## 4. Tweaks: `[tweaks]` in SWOS.ini

A tweak changes how the original behaves where the original annoys: small, self-contained,
**off by default**, one key each. First ones:

| Key | What it does | From |
|---|---|---|
| `cpu_cards` | the computer's players are booked and sent off too | petarku, benefactorr |
| `no_teammate_tackles` | a team-mate does not tackle the player on the ball | a Reddit report |
| `tackle_controlled_player` | a slide tackle is made by the player you control, not another | a Reddit report |

Before any of these is written, **check it against the original** (`data/SWOS2.s`, and
`swos.asm` for DOS): a report is not automatically right. If the original does it, it is a
tweak; if only OpenSWOS does it, it is a bug and is fixed in the base for everyone.

A tweak that changes a match is **match rules online**: it travels in the host's rules like the
lobby's switches (SHORT PRESSES, CARDS/INJURIES: `include/netplay_match.h`), the joiner plays
the host's, the recorder and `.SRP` record it, and adding one raises `NETPLAY_COMPAT`. The
golden careers and the replay corpus run with every tweak off, so they keep proving the original.

**A mod may switch a tweak ON -- the owner, 2026-11-04, for Career+'s "more fouls" and "the
AI substitutes its injured players".** The rules:

1. **The tweak is the game's, not the mod's.** It is an ordinary `[tweaks]` key, built in, off
   by default. A mod cannot add one or change what one does; it can only switch on one that
   is marked OFFLINE-ONLY, through one call, `ModApi_SetTweak(slug, "cpu_cards", 1)` (`src/tweaks.c`
   keeps a mod's switches apart from the player's, and which mod made each; callable from
   `init`). A tweak that is match rules online is never a mod's to switch (`byMod` 0).
2. **Online always wins.** A match against another player plays without it, whatever a mod or
   SWOS.ini says; so do the rigs and the golden careers. The mod stays a `career` (or `modes`)
   mod: it never has to be alike in both games.
3. **The player can see it.** The tweak's row in OPTIONS shows who switched it ("ON
   (CAREER+)"); turning the mod off puts the tweak back to the player's own setting.
4. **Replays keep it.** A recording stores the tweaks in force, so a replay or `--srp-resim`
   plays the same match.

## 5. The original, always buildable

Every behaviour that differs from the Amiga game -- tweaks, mods, the worlds, gameplay styles
the original never had -- is compiled in only under a switch, so one flag builds the original:

- `SWOS_ORIGINAL=1` (both makefiles): no tweaks, no mod loader, no worlds (`SWOS_WORLDS=0`, which
  exists), only the AMIGA and DOS gameplay styles. Additions that do not change how the game
  plays (widescreen, netplay, the setup) are not divergences and stay.
- New divergent code is written behind its switch from the start (as `SWOS_WORLDS` code is:
  CLAUDE.md, "new world code must keep that true").

## 6. Pitches: Tile Agent's format, in the base

The pitch becomes a Tile Agent map: layers, some above the players, and animations with easing
(`docs/PITCH_FORMAT_V2.md`; the format is Tile Agent's own, `D:\Projects\GitHub\TileAgent`
`docs/FORMAT.md`). Stage 1 is in the game: a DOS-graphics pitch drawn from a `.tmj`
(`docs/PITCH_MAPS.md`, `[graphics] pitch_maps`). It is base, not a mod, because it is a format
the engine reads; the pitches made with it are mods.

- **SDL** reads the `.tmj` and its images directly (the runtime in `third_party/tileagent`).
- **The Amiga reads a binary**, never JSON (parsing JSON on a 68k takes seconds per file):
  `.PCH`, the layout in PITCH_FORMAT_V2.md §6 -- tile indices not offsets, big-endian, a magic,
  a version and a **capability word**. It takes the base layers and the crowd's animation and
  refuses a pitch that needs more (over-sprite layers, alpha, many animations) cleanly. Chip RAM
  has ~4 KB headroom beyond the 82 KB pitch buffer, so a pitch must fit what the game has.
- **Who writes the binary:** one C writer, in the Tile Agent runtime, used by **both** Tile
  Agent's export and OpenSWOS Setup. An author exports `.PCH` from Tile Agent; a mod that ships
  only the `.tmj` gets its `.PCH` made by the setup when it builds an Amiga drawer. One writer,
  so the two never disagree.
- Next stages (PITCH_MAPS.md, "what the map could take over next"): the crowd's behaviour, the
  adverts, the flags and goals from the map instead of the engine's code; then the AGA and OCS
  tiers' pitches as maps too.

## 7. The Amiga OCS/ECS target

The original's graphics on the original's chipset, as its own build beside the AGA one:
`make -f Makefile.amiga OCS=1` -> `bin/SWOS2_OCS`, the 4-bitplane `grafs/` tier, without
`#define AGA` (`include/display.h`: the switch exists, last verified before the recent AGA work,
docs/AGA.md). Its own SWOS drawer in the setup. To measure first: the binary's size and what it
needs of chip and fast RAM -- the AGA build needs 8 MB of fast; an A500 or A600 with an
expansion, or an emulator set up as one, is the likely floor, and the doc will say so.

## 8. What the engine needs (the order to build it)

1. **The overlay and the manifest.** A mod is a folder with `mod.json`: id, name, version,
   author, targets (`sdl`, `amiga`, both), what it changes (`cosmetic`, `gameplay`, `career`),
   its files per target, and for the Amiga the sizes it needs. `swos_data_path()` on SDL and the
   resload file calls on the Amiga look through each enabled mod, in order, before the base data.
   The enabled list: `[mods]` in SWOS.ini, `data/MODS` in an Amiga drawer. On the Amiga a mod
   replaces a file, not memory: files already load on demand into their own buffers.
2. **Registries instead of edits.** A mod adds menus and rows at named insertion points, strings
   with their translations, and settings with their OPTIONS rows. On the Amiga a mod ships its
   menus already packed (the binary the JSON loader makes today), never as JSON. (2026-11-05: the
   Amiga builds them from the JSON at their first show instead, about a second for a screen --
   §30. Packing them is for when that is too slow.)
3. **The ruleset.** One structure the match reads instead of constants: players per side, the
   pitch's size and walls, match length, card and substitution rules, physics parameters, the
   tactics set. Much of Indoor becomes a ruleset plus art; what is left becomes generic features
   in the base (walls, time penalties).
4. **Match setup.** Who plays, the starting state, how it ends, how it is scored: shooting
   practice, penalties and challenges become data.
5. **Career events and saves.** Season start and end, the transfer window, AI decisions, as
   hooks; each mod a named section of the JSON save (named fields, never addresses: CLAUDE.md).
6. **The online contract.** A `gameplay` mod's id, version and hash go in the handshake, and two
   builds whose gameplay mods differ do not start a match (like a different `NETPLAY_COMPAT`).
   `cosmetic` mods may differ. **The goal (the owner, 2026-11-04): mods in multiplayer** -- two
   players with the same gameplay mods, at the same versions, play each other; the matchmaker
   lists a game only to players whose gameplay mods match (as it does by `NETPLAY_COMPAT`), and
   the lobby says which mod is missing or differs. **Built (§17):** the handshake refuses a
   player whose gameplay and data mods differ (uuid, version, files). Tweaks travel the same way, in the host's rules (§4). Recordings carry the mod
   list, so a replay and `--srp-resim` play by it. A gameplay mod's match state registers with the rollback registry (`src/sim_state.c`).

## 9. Code mods

**Source mods first.** `mods/<id>/` with its sources and `mod.json`, built into the binary
(like `fork.mk`), enabled or not at run time from the list in §8.1. They work on every target,
the Amiga, iOS and the web included, and stay deterministic. They call the hooks of §8; they
never patch the engine's code. They are how the hooks get tried on real cases: Indoor and
Career+ are the first two to port.

**Lua at the same time.** Lua 5.4 (MIT: fine beside GPL-3.0-or-later), embedded, calling the
same hooks as the source mods -- a script can do what a source mod can, through one API.

- Runs on every SDL target (desktops, phones, the web, handhelds).
- Numbers are **integers** for anything a match or career sees (a `luaconf.h` with 32-bit
  integers): floats differ across machines and the Amiga has no FPU, and both peers of a match
  must compute the same.
- The Amiga builds `-nostdlib`, so Lua there needs the small libc it uses (allocation over the
  game's heap, strings, `setjmp`); a 68020 is fast enough for menus and season events, **not**
  for anything run per player per frame. A mod says whether its scripts are needed on the Amiga.
- Scripts are sandboxed: no files outside the mod's folder, no network, no OS.

Native modules (`.so`/`.dll`, an Amiga LoadSeg module) are not planned: per-target, impossible
on iOS and the web, and broken by every engine change.

## 10. Distribution

One manifest format and one index for every mod manager: OpenSWOS Setup on a PC or Mac, SWOS
Launcher's DLC Manager on the Amiga (over Roadshow), the phone copy. An index entry says which
targets a mod is for -- which also gives SWOS United and SWOS United Amiga their own downloads.
Mods are hosted by their authors (content with other people's rights stays theirs, as World
2026-27 is Davide's); the index only points to them, with each file's hash.

## 12. Built so far

**The overlay (§8.1), both targets** (`include/mods.h`, `src/mods.c`):

- **SDL:** `[mods] enabled = a, b` in SWOS.ini (or `--mods=a,b`, or `SWOS_MODS_ENABLED` for one
  run). Mods are folders in `mods/` in the player's game folder (`$SWOS_MODS` elsewhere), each
  with a `mod.json`; one whose `targets` lacks `"sdl"`, or with no folder or manifest, is left
  out and the log says why (`[mods]` lines). `swos_data_path()` looks in each mod, in order,
  before the assets folder and the game's own files; `swos_data_path_base()` (saves, deletes)
  never does. Mods start before translations load, so a mod can carry its own.
- **Amiga:** the drawer's `data/MODS`, one id a line (an id ending in `*` is not cosmetic),
  read at the first file read; `make_read_path()` in `src/resload.c` looks in
  `PROGDIR:mods/<id>/` (or `mods/<id>/` under WHDLoad) for every load, never for a save.
- **Online:** a mod whose `changes` is not `"cosmetic"` (or says nothing) keeps MULTIPLAYER
  off ("TO PLAY ONLINE, TURN OFF THE MOD ..."), until §8.6.
- **Checked:** SDL -- a test mod's `en.json` renamed an OPTIONS row (screenshots with and
  without), MULTIPLAYER refused with a gameplay mod; Amiga (FS-UAE) -- a test mod's
  `grafs_aga/MENUBG.RAW` replaced the main menu's backdrop (screenshots with and without);
  `--menu-selftest` and `scripts/replay_v2_test.sh --all` unchanged with no mod.
- **OpenSWOS Setup installs mods** (`tools/swosdata/app/main.cpp`, "the mods"): the **Mods** extra
  on its first screen adds a Mods screen -- the mods installed (canonical and DLC), each On / Off
  (`[mods]` of this computer's SWOS.ini, the list the game reads) and Remove (a DLC's folder);
  a mod's `.zip` dropped on the window, picked with "Install a mod...", or found in Downloads is
  installed: its `mod.json` (at the zip's root or in one folder) checked as the game checks it
  (a uuid; `sdl` or `amiga` in its targets; not a canonical uuid), the folder put in the
  player's `mods/<slug>` (slug: the manifest's `id`, else the zip's name; the same uuid under
  another slug is replaced), turned on. `--mod-install=ZIP` does it without the window. Making an
  Amiga drawer copies the mods that are on and made for the Amiga into its `mods/`, and writes
  `data/MODS` (no `data/MODS` when none is). Checked: an install, a refusal (no uuid), the
  screen with a mod in Downloads, a drawer with `data/MODS = indoor-hall*`, the German screen.
  **Everywhere the setup puts the game, the mods that are on go too**:
  - the **WHDLoad package**: staged as a drawer gets them, its `mods/` and `data/MODS` in the
    package's `data/` (`SwosData_MakeWhdload`'s `modsDir`);
  - a **phone**, over the Wi-Fi copy: the setup lists each mod's files as `mods/<slug>/...`
    beside the assets and sends `[mods]` in the phone's SWOS.ini; the phone (`src/phone_fetch.c`)
    puts them in its own mods folder, replaced whole once everything came (a setup that sends
    no mods leaves the phone's as they are);
  - a **handheld's card**: into the port's player folder, `swos/conf/.swos/mods/`, with
    `[mods]` in its SWOS.ini.
  Checked: the phone copy end to end (a Windows setup, the Linux game's `--phone-fetch`: the
  mod in its mods folder, `[mods] enabled` in its SWOS.ini); the handheld copy
  (`--handheld-copy`); a WHDLoad package (its log: 2 mod files; the names in the archive).
  Not yet run on a phone, a handheld or under WHDLoad itself.

**The first tweaks (§4)** (`include/tweaks.h`, `src/tweaks.c`): `[tweaks]` in SWOS.ini, each
`true | false`, off by default; off online and under every rig (`Tweaks_On`); the Amiga has none.

| Key | The original (checked: SWOS2.s and swos.asm agree; our C matched) | The tweak |
|---|---|---|
| `cpu_cards` | `TryBookingThePlayer` / `TrySendingOffThePlayer` give no card to a side with no human (SWOS2.s:26026) | `src/tackle_foul.c`: every side by the same rolls |
| `tackle_controlled_player` | whichever of the controlled player and the pass receiver is nearer the ball slides (SWOS2.s:30408-30431 and 31116-31146) | `src/update_players.c`: on a human's team only the controlled player slides |
| `no_teammate_tackles` | the receiver runs onto the ball (`passingBall`), may slide on your fire press and is handed control on reaching it (SWOS2.s:31146-31215) | while a human's controlled player has the ball (within 72), the receiver comes to support distance only: no slide, no hand-over |
| `more_fouls` | `PlayerTacklingTestFoul` waves on every tackle not from behind (direction more than 1 apart) | one in 16 of those is a foul -- its roll (`Rand`) taken only with the tweak on (benefactorr's Career+) |
| `ai_injury_subs` | the computer never substitutes: `BenchCheckControls` answers only a player calling the bench | at a stoppage, the computer replaces an injured player with the bench player nearest his position (the keeper by the reserve keeper), within its substitutes; never the managed career club (benefactorr's Career+) |

Checked: with every tweak off, `rollback_test.sh --all`, `replay_v2_test.sh --all` and
`netplay_test.sh --all` pass; both targets build. **Not yet played with the tweaks on.**

## 13. SWOS United: a thin fork plus a mod (agreed 2026-11-04)

SWOS United (github.com/SWOS-United/SWOS-United) is three things, and only two are a mod:

| Part | Where it goes |
|---|---|
| SWOS 2020's online look: MATCH MAKING, RANKINGS, LEAGUES, the lobby, CHOOSE GAMEPLAY's icons | **the United mod** -- menus and their handlers, through the registries (§8.2) |
| accounts and its own servers: SWOS-API log-in, swos.swosunited.com's rankings and leagues, its matchmaker | **the United mod**, as a source mod (it talks to the network and handles log-ins: not a sandboxed script), through a new **online-provider hook**: which server, how to log in, where rankings and leagues come from |
| its identity: name, icon, phone app ids (`com.swosunited.game`), installer, player folder, netplay tag | **stays the fork**: `include/project_identity.h`, its packaging and icons. A mod cannot rename an app or give it an installer |

The aim is a **thin fork**: `project_identity.h`, packaging, icons and the mod -- no shared file
edited, so a merge of OpenSWOS never conflicts. (The merge of 2026-11-04 had five.)

**Order:** after the registries (§8.2) and the online contract (§8.6). The online-provider hook
is designed with United as its first user, and **with United's team**: it changes how they work.
It is also the hook any fork uses for its own online service (FORKING.md: a fork runs its own
server).

**Syncing United while it moves -- the care it needs:**

- **Until the hook exists, United stays a full fork** and merges OpenSWOS as today
  (`git merge upstream/main`, never rebase; FORKING.md). Its online code is where conflicts
  come from (`src/online_menus.c`, `src/platform_sdl.c`, `include/project_identity.h`).
- **Move United's code into its mod one piece at a time**, each piece in its own United commit:
  a screen goes into `mods/united/` as soon as the registry it needs exists in OpenSWOS, and its
  edits to the shared file are removed in the same commit. Never half-move a screen.
- **Each sync, after the merge:** build both targets; `--menu-selftest`; check the identity
  header kept United's values (app id, tag, servers) and that player-facing paths name
  `com.swosunited.game` (the Android folder in INSTALL.md and the install page); and log in
  and play a match through United's own server, which OpenSWOS's tests never reach.
- **Shared decisions stay explicit:** where OpenSWOS and United both have a feature (XBOX in
  CHOOSE GAMEPLAY, 2026-11-04), the merge keeps OpenSWOS's in OpenSWOS's look and United's in
  its own; a conflict there is resolved by asking, not by picking a side.
- **OpenSWOS never merges United** (FORKING.md); a United fix OpenSWOS wants is cherry-picked.

## 14. Canonical mods and DLC mods; every mod a UUID (the owner, 2026-11-04)

Some of SWOS 2020's features become mods, so mods come in two kinds:

| | **Canonical** | **DLC** |
|---|---|---|
| What | part of OpenSWOS: maintained in the repo, shipped in every drop, tested with each release | downloaded: by its author, or the project's, hosted outside the game |
| Where | the game's own `mods/` (`MODS_CANONICAL_DIR`; `bin/mods/`, git-tracked) | the player's `mods/` folder (`Mods_Root()`), put there by OpenSWOS Setup or the Amiga DLC Manager |
| Rights | only what OpenSWOS may ship | anything its author may share. **Content with other people's rights is always DLC**: World 2026-27, SWOS 2020's cups (HISTORIC TOURNAMENTS' data), the SWOS 2020 pitches. The engine capability that reads it can be canonical (the `.DIY` reader is base) |
| On | when its manifest says `"default": true`, unless `[mods] disabled` names it; or when `[mods] enabled` does | only when `[mods] enabled` names it |
| Online | matched like a DLC when it changes the match: on in one game and off in the other is a different game (§17) | matched by uuid, version and the hash of its files (§17) |

**Every mod has a `uuid`** in its `mod.json`, separate from its folder's name (the slug, a
readable label that may change). The uuid is the identity in saves (a career made with a career
mod records its uuid and version), the handshake, recordings, the index, and dependencies.

- **Canonical:** `uuid5(NAMESPACE, "mod/<slug>")`, NAMESPACE being the project's
  (`af19cc5a-6529-537b-935b-407bd73b75fb`, scripts/assign_team_uuids.py), written into the
  manifest once and never changed:
  `python3 -c "import uuid;print(uuid.uuid5(uuid.UUID('af19cc5a-6529-537b-935b-407bd73b75fb'),'mod/<slug>'))"`
- **DLC:** a random uuid4, made by its author when the mod is made.
- **Refused** (the log says which): a mod with no uuid; a second mod with a uuid already on; a
  DLC with a canonical mod's uuid. The Amiga reads no manifest, so it trusts the setup's
  `data/MODS`, which the setup writes from manifests it has checked.

**Order:** the `[mods] enabled` list first, in its order (a slug that is a DLC folder is that DLC,
else the canonical mod of that slug), then the canonical mods on by default. A file two mods
have comes from the first.

When the first canonical mod lands, add `mods` to the trees every drop stages
(`build_dist.sh` FULL_DATA_DIRS, `build_installer.sh` DATA_DIRS, `make macos-app`,
`packaging/mobile/CMakeLists.txt`, `build_portmaster.sh`, the Amiga drawer), as the other
tracked `bin/` trees are.

Checked (SDL): a DLC with no uuid refused; a DLC with one on; a DLC with a canonical uuid
refused; a canonical mod on by default and off with `disabled`. Both targets build.

## 15. Registries (§8.2): what exists, what is built, what comes next

**What a mod can already do on SDL, through the overlay alone** (found 2026-11-04):

- **Replace any menu.** The original's 47 menus are rebuilt from `data_json/menus/*.json` at
  every start (`MenuJson_InstallAll`, on by default), and those reads go through the overlay;
  the SWOS 2020 and OpenSWOS menus load from JSON when first shown. Limit: an original menu may
  not grow past its compiled size (it is written over the compiled bytes; a bigger one is
  skipped and logged) -- growing one needs MENUS.md §1e's call-site repoint.
- **Replace formations** (`data_json/tactics`, on by default) and the career parameters
  (`career_params.json`).
- **Replace a country's clubs** (`data_json/teams/<COUNTRY>.json`, the database's format with ids
  of the mod's own: docs/TEAM_IDS.md), with its leagues (`competitions/leagues.json`). A country's
  clubs have a range of global team numbers sized to 96/97's; a mod's file with more clubs grows
  it at start-up and moves every later country's (`DataJson_FitModTeamFiles`, as a world's do),
  so the league tables keep them apart. Career+'s Yugoslavia is the case: 24 clubs where 96/97 had
  10, which ran into Algeria's and Argentina's numbers (panic 0x5555 in its first season).

**Built: strings** (`src/translations.c`). A mod's `data_json/translations/<lang>.json` holds
only the strings it adds or changes, and is **merged** over the game's: each key it has
replaces the game's or joins the table, the first mod in the list winning a key two mods have.
The game's own file is read without the overlay, so a mod never replaces the whole table.
Checked: two mods each renaming an OPTIONS row and both renaming a third -- both renames shown,
the first mod's winning the shared one.

1. **A MODS screen** (OPTIONS -> MODS) -- **built** (`src/mods_menu.c`,
   `openswos/modsMenu.json`): every mod on disk (`Mods_Scan`), canonical then DLC, up to 8 rows
   of name, version and kind with ON / OFF / CANNOT (a mod that cannot be on: fire says why);
   fire turns one on or off, written to SWOS.ini at once, played from the next start. OPTIONS'
   value says how many are on; hidden on the Amiga (its list is data/MODS). Checked: the screen
   with a canonical, a DLC and a broken mod; toggling both kinds wrote `enabled=hall`,
   `disabled=classics` and the next start played by it; `--menu-selftest` covers it. Still to
   come: each mod's own page (its settings, item 2), more than 8 mods. Mods add to the game **there, and at named hooks**, rather than by
   squeezing rows into the original's screens -- those keep their layout, so `SWOS_ORIGINAL`
   stays the original and two mods never fight over one row.
2. **Mod settings.** `mod.json` `"settings": [{ "key", "label", "choices": [...], "default" }]`,
   kept in SWOS.ini `[mod.<slug>]`, shown on the mod's page, read by its code
   (`Mods_Setting(uuid, key)`).
3. **Named hooks** where a mod's content appears in the game: "competitions from mods" in
   PRESET COMPETITION (HISTORIC TOURNAMENTS is its first user), then modes (FRIENDLY, the main
   menu) as mods need them -- each a generic entry the engine draws from what mods register.
4. **Handlers.** A data-only mod's menus use the handlers the game already has (the menu
   symbol registry, `_menuSymbols`); a code mod (§9) registers its own as `<slug>.<name>`.
5. **The Amiga** has no menu symbol registry (`menu_symbols.c` is SDL-only) and no run-time
   translations. Its mod menus will be packed binary (scripts/menu_json_to_bin.py, MENUS.md
   §3) whose references are indices into a compact Amiga registry; measure its size first.

## 16. Built-in mods and their hooks (2026-11-04)

A **built-in mod** is code in the game with a canonical manifest (`bin/mods/<slug>/mod.json`), the
first kind of code mod (§9) and the way a feature that is "different" (§3) ships without a fork:
its code runs only while the mod is on (`Mods_IsOn`), turned on or off on OPTIONS -> MODS like any
other. The code runs at **hooks**, fixed points of the engine, never patches of it
(`include/mod_hooks.h`, `src/mod_hooks.c`: one row per mod, its slug and its hooks):

| hook | where | what may be done there |
|---|---|---|
| `ModHooks_FrameDrawn(renderer)` | `platform_sdl.c`'s present, after the frame and its HUD, before the CRT effects, the touch controls and the swap | draw over the finished picture in its logical size. Runs once per frame SHOWN, so never on a re-simulated one: the place to keep a mod's own state |
| `ModHooks_PitchDrawn()` | `game_loop.c`, after `ScrollToCurrent` drew the pitch into the frame being made, before the sprites | draw into the 8bpp frame UNDER the players. The frame may be one GGPO re-simulates and never shows, so only draw here |
| `ModHooks_PlayerSetsRaw()` | `color_sprites.c` ConvertColorsAndTextSprites, once a match, before the player sets are recoloured | read the raw art (team 1's first set, sprites 227..327) |
| `ModHooks_ReplayFrameBegin(first, fresh)`, `ModHooks_ReplaySprite(image, left, top)` | `highlight.c` DrawReplayFrame (the in-match replay) and `replay_v2.c` ReplayV2_DrawFrame (VIEW's .SRP): the pitch drawn, before the sprites; then each recorded sprite | draw under the replay's sprites; learn where its players are (`ModApi_ReplayPlayerFeet`) |
| `ModHooks_PlayerDrawn(sprite, gfx, x, y)` | `sprites.c` DrawQueuedSprites, right after a player sprite is drawn, before anything is drawn over it | redraw that sprite's own pixels, draw beside it; draw only, as PitchDrawn |

optional, defined in its own `src/mod_<slug>.c` and listed in `src/mods_builtin.c`. A fork lists
its own in `src/fork_mods.inc` (`extern const ModDef ModDef_<slug>;` lines, then
`#define FORK_MOD_LIST &ModDef_<slug>,`), a file OpenSWOS does not have, so a merge never meets
it. `init` runs at start-up (after the mod list, before the menus are built from JSON);
`src/mod_hooks.c` calls every hook of every mod that is on. The hooks, by what they are for
(include/mod_api.h says each one's exact point):

| what | how | where it runs |
|---|---|---|
| drawing | `frameDrawn`, `pitchDrawn`, `playerSetsRaw`, `playerDrawn`, `replayFrameBegin`, `replaySprite` | the table above |

| entries (H1, H6) | `ModApi_AddEntry(point, slug, label, fn)` in `init` | `MODPOINT_MODES`: the main menu's **MODES** button (entry 16, above CREDITS; shown only while an entry is there, never on the Amiga) opens `openswos/modEntriesMenu`, the list; `MODPOINT_AFTER_MATCH`: the same list after a friendly the player played (`game_loop.c`, after its REPLAY / EXIT). `ModApi_ShowEntries(point)` shows any point's list from a fork's own screen |

| settings (H7) | mod.json `"settings"`; `ModApi_Setting / SettingInt / SetSetting` | SWOS.ini `[mod.<slug>]` (Settings_Save keeps sections it does not know); the mod's page: OPTIONS -> MODS, fire on its name (`openswos/modPageMenu`), fire cycles a choice. The weather mod's two |

| a match of its own (H2, H4) | `ModApi_DefaultSetup`, `ModApi_PlayMatch(slug, &setup, &result)` -- blocks until it is over; then `ModApi_EndMatch`, `StartShootout`, `Score`, `MatchFrames`, `ModMatch(slug)` | `src/mod_match.c`: a friendly without its menus, as the arcade cabinet plays one -- the teams by id (file << 8 \| ordinal), each side CPU / player 1 / player 2 (`SetupPlayers` asks no one), pitch, length, subs, extra time / penalties / straight to a shoot-out, replays, the stadium screen and the REPLAY menu or not, the match's name, the score and the minute (0-44) at kick-off (`InitGameRestoreTeams`' end); the friendly's own settings put back after. **The mod API** (`include/mod_api.h`, `src/mod_api.c`): what a mod asks the game -- whether a
match or a replay is on, the pitch type and minute, the players (where, facing, face, name),
the camera, the screen, the frame to draw into, the palette, its own folder -- never the game's
globals, so an engine change changes mod_api.c and no mod.

Neither may write match state: the frame buffers are not in it (`src/sim_state.c`), and a mod's
own state must not be either. A built-in mod that is cosmetic plays online like any other
cosmetic mod. No random number the game draws may be taken (`Rand`, libc `rand`): a mod keeps
its own generator.

**`weather`** (off by default; `src/mod_weather.c`): the first built-in mod.
- **The weather.** C4ppy77's pitch-weather (`third_party/pitch_weather`, MIT, ported to C:
  `OPENSWOS.md` there), drawn at FrameDrawn with `SDL_RenderGeometry` (SDL 2.0.18; built only where
  the SDL has it, `src/pitch_weather_impl.c`). From the match's pitch type: frozen snow, muddy
  heavy rain, wet rain, soft drizzle, none on the others. Its intensity drifts over the 90
  minutes (the clock's minute) from a seed taken at kick-off from real time.
- **The mud.** On a muddy, wet or soft pitch every player leaves footprints: one every 5 pixels
  he moves on the ground, left and right foot either side of his way, none across a jump (a
  restart). They are added and aged at FrameDrawn (so a rollback never doubles them) and
  stamped at PitchDrawn, a pixel at a time through a palette table: each entry's nearest entry
  in the palette shown toward a dark earth brown, at three strengths, rebuilt every second (a
  match's palette fades). A print starts dark and dries through the three, and in the last
  quarter of its life its pixels go one by one, so the pitch never fills up: 14 s on muddy, 8 s
  wet (both starting at full strength), 5 s soft (starting a level lighter). Both palettes, the
  Amiga's and the PC's, take it. A replay has a trail of its own (the match's waits), made at
  ReplayFrameBegin from the players its last frame showed, each followed by the nearest of where
  they were; it starts again at a replay's start or a jump.
- `SWOS_WEATHER_PITCH=<0..6>` plays a pitch type's weather and mud whatever the match's -- for a
  test: `SWOS_WEATHER_PITCH=1 SWOS_PRESENT_CAPTURE=150 SWOS_PRESENT_CAPTURE_FROM=1500
  bin/SWOS.x86_64 --mods=weather --replay-test=../tests/replay/<a .swr> --dos-graphics=off`
  writes the presented frames as `swos_presentNNN.png`.
- **The splashes.** On a rain pitch, drops hitting the pitch, in the pitch's own cells of 32
  pixels (so they stay where they hit as the camera moves): 4 slots a cell, a share of them
  raining (150 heavy, 90 rain, 35 drizzle a screen at full intensity, times the weather's), each
  landing a drop every 360 ms somewhere new in its cell -- a dot, a crown, a ring going, 60 ms
  each -- stamped under the players through a lightening palette table. Real time.
- SDL only (`"targets": ["sdl"]`): neither hook exists on the Amiga.

**`hair`** (off by default; `src/mod_hair.c`): players with more than one head of hair.
- At PlayerSetsRaw the raw frames are kept, with where each one's hair is (raw 9, 12, 13). At
  PlayerDrawn an outfield player's frame is made again for his look, in raw colours, and every
  pixel that changed is written through his face's colour table, only where the frame still
  shows his sprite's pixel.
- **Looks**: blonde (face 3's yellow and orange), black, receding (the 96/97 Mod's 'E' shape:
  the hair's top row skin, and the next row's hair with a pixel on both sides), shaved (the
  skull's tone, nearest the palette has to the Mod's), ponytail (the owner's 3x3 PONYTAIL.bmp in
  hair colour 9: as drawn facing left, mirrored facing right, down the back facing away, unseen
  from the front; upright frames only). Goalkeepers keep theirs.
- **Who looks how**: `looks.csv` in the mod's folder (the Mod's `bald-looks` format:
  `country,club,name,look[,face]`, matched by full name and club), else a hash of his name (7%
  receding, 6% shaved, 4% ponytail; white 14% blonde, 10% black; ginger 30% black), so a player
  always looks the same. `SWOS_HAIR_LOOK=<look>` gives everyone one (a test's).
- **Marco's shaved art** (the Mod's `tools/shavedart.json`, per frame per skin) is used when it is
  in the mod's folder as `shavedart.json`, else the hair becomes the skull's colour, its lowest
  row a shade. Neither it nor the Mod's `packs/bald-looks-2627.csv` is in this repo: the Mod's
  data is not MIT (its LICENSE §2) -- the owner asks Davide and Marco first.

**Online: the same mods play each other** (the owner, 2026-11-04). What a mod changes:

| `"changes"` | means | online |
|---|---|---|
| `cosmetic` | how the game looks or sounds | never matters |
| `modes` | matches and screens of its own; a normal match untouched (practice, challenges) | never matters |
| `career` | careers and their saves | never matters |
| `gameplay` | how a match plays | both players need it alike |
| `data` | what a match plays with: teams, a world | both players need it alike |

A mod that says nothing counts as `gameplay`; canonical mods are no exception (one game can
have a canonical mod on and the other off). `Mods_OnlineSignature` hashes, in uuid order, each
such mod's uuid, its version and a hash of all its files (taken at start-up), so a copy edited
by hand or half updated is another mod. The handshake (`src/p2p_link.c`, protocol 6, the setup
packet's bytes 32-35) refuses a player whose signature differs: **YOUR MODS ARE DIFFERENT / BOTH
NEED THE SAME MODS: OPTIONS, MODS** (`P2P_FAIL_MODS`; the self-test's case 4f). The world mod
plays online because the server checks both teams against its list anyway (`TeamRegistry.inc`,
which carries the world's teams). `NETPLAY_COMPAT` 10. Next: the matchmaker lists a game only to
players with the same signature (as it does by `NETPLAY_COMPAT`), and the lobby names the mod
that differs.

**For forks' screens** (SWOS United's asks, 2026-11-04): `ModApi_FindEntry(point, slug)` and

## 27. Career events and a mod's section of the career save (§8.5; Career+'s §3.4)

A `career` mod's ModDef has career hooks (include/mod_api.h). They run only while the mod is
on, never on the Amiga, never in a match and never online. Unlike the other hooks, a career hook
may change the career: its squads and its players, through the game's career code.

| hook | runs |
|---|---|
| `careerNew()` | `InitCareer`: the new career's clubs set up, before its first `InitializeNewSeason` |
| `careerSeasonEnd(season)` | the end of `ContinueCareerNextSeason`, after either job branch: the next season set up (`season` its index) |
| `careerBeforeContinue()` | `ContinueCareer`, before the season's menu: may show a mod's menu (RETIREMENT NEWS) |
| `competitionFinished(r)` | each title of the season end, as `career_season.c` decides it: every league division once its table is settled (before the moves are counted), the career country's main cup, its second and third cups, and the European cups' holders (after `Career_UpdateUefaCupCompetitionSlot`). `r`: the season, `comp_id`, `ModCompKind`, the division, the winner's team id. A title with no winner (0xFFFF) is not told. |
| `playerMoved(m)` | a buy (`Career_RemovePlayerAndAddAsTrialist`: his club's slot -> your free slot) and a sale (`Career_TransferPlayerAndAddReplacedToMarketPool`: your slot -> the buyer's slot of the player he replaced) |
| `playerCreated(c)` | a new player made by the game, who the hook may change: a trialist in the career club (`Career_GenerateTrialistForTeamPlayer`, and `Career_ConvertPlayerToTrialistFromName` for the training match's), and the player another club gets in place of the one you bought (`MODPLAYER_REPLACEMENT`) -- before that club's copy goes into the career pool |

A squad's line-up changes only reorder the career club's index list (`_currentMatchPlayers`); a
player keeps his slot in the team file, so they are not moves.

**The save.** A mod's `careerSave(out)` writes its object's members with `ModJson_Printf` (named
fields, never addresses: CLAUDE.md); the career's JSON gets `"mods": {"<slug>": {...}}` after
its last member, and only when a mod that is on wrote something, so a career without career
mods saves as it always did (the golden careers). On load, after the career's pointers are
rebuilt, each mod that is on gets `careerLoad(json, len)`: its object, or NULL / 0 when the save
has none (start its records empty). The loaded career's "mods" members are kept as their text:
a mod that is off this session has its section written back unchanged at the next save, so
turning Career+ off for a while loses none of the career's Career+ data; a mod that is on and has
careerSave writes its own instead. A new career keeps none.

## 30. Mod code on the Amiga (2026-11-05)

The owner: "we must add mod support for the Amiga after Career+". The built-in mods' code now
builds into the Amiga binary too: one mod API, one set of hooks, the same `src/mod_<slug>.c` on
both targets. Run-time loading of mod code (LoadSeg, a script language) is still not planned (§6).

**What makes it build there:**
- **A C library.** The m68k toolchain has none (its only header is a three-line string.h).
  `include/amiga_libc/` (stdio, stdlib, string, ctype, stdint) is on `Makefile.amiga`'s
  `-isystem` path only, and `src/amiga_libc.c` is behind it: `snprintf` with flags, width and
  precision (no floating point -- none of the mods print one; 64-bit decimal without libgcc),
  `malloc`/`free` over `swos_io_alloc` (Exec, or WHDLoad's heap), `strtol`, `qsort`, the `str*`
  calls, and `getenv` = NULL. `fprintf`/`printf` go to `_gAmigaLog`, a 4 KB ring in `.data` that
  the harness reads (`_gAmigaLogPos` bytes written so far). It has no file calls on purpose: a
  mod's file goes through swos_io/resload, so the mod overlay and WHDLoad apply.
- **The JSON menu loader** (`src/menu_load_json.c`). A mod's screens are JSON menus, built at
  their first show and then kept. The writer lays words down in host order. The game's own menus
  stay compiled on the Amiga. A mod menu there resolves its own handlers (`ModApi_RegisterHandlers`)
  and two of the game's symbols, `SetExitMenuFlag` and `_aExit` (the only two any mod menu names;
  add one to `menu_resolve` in that file when a mod needs it). **It costs time:** TEAM TRAINING's
  7.5 KB of JSON took 52 VBlanks (about a second) to build on an emulated A1200. That happens once
  per menu per run, which is why §8.2's packed binary menus are not needed yet.
- **The hook sites** in the game are no longer SDL-only, except where the hook itself is: the
  renderer's `frameDrawn` (no renderer: `SDL_Renderer` is an opaque type, so a `ModDef` is the same
  struct on both targets), the replay viewer's `replayFrameBegin`/`replaySprite` (no `.SRP`),
  LIVE CAST, the online provider, the menu extras and the OPTIONS -> MODS screen.
- **Mods start** in `mainC` (src/SWOS.c) before the front end, after resload has read `data/MODS`.

**What the API answers differently there** (include/mod_api.h says so at each call):

| | the Amiga |
|---|---|
| `ModApi_Ticks` | the VBlank count x 20 ms |
| settings (`ModApi_Setting`, `SetSetting`) | no SWOS.ini: a mod's defaults, and what it sets is kept for the run |
| save files (`ModApi_SaveFile`/`LoadFile`) | `save/<slug>_<name>`: resload makes no folders, and FFS names are 30 characters |
| `ModApi_ListFiles` | `Resload_ListDir`: the mods' folders first |
| competitions | JSON `.DIY` only (no DOS `.DIY`); no assets folder, no whole-match replay |
| teams | no team database: `ModApi_TeamByUuid` is 0, so a mod gives the team's number too (`ModApi_TeamByUuidNumber`: taken when the uuid is the one derived from it, docs/TEAM_IDS.md -- one SHA-1, src/team_uuid.c); `ModApi_ChosenTeamUuid` derives a 96/97 team's; `ModApi_TeamPlayer` reads the team file |
| team packs, netplay, the ticker row | none (0, `ModMatch_Quiet` 0, -1) |
| `ModApi_PaletteColour`/`NearestColour` | not yet: they come with the first mod that draws there |

**Which mods:** `src/mods_builtin.c` lists a mod with `MOD_AMIGA` once it builds and plays there,
and `MOD_SDL` until then; its `mod.json` `"targets"` then includes `"amiga"`, which OpenSWOS Setup
reads to copy it into an Amiga drawer and list it in `data/MODS`. Ported: **practice**, **euro36**,
**speedrun**, **challenges** (and the data mod **challenge-collection**: its files carry each team's
number, `"team": "5017"`, beside the uuid, and the editor writes it too). Not yet, each for a reason
of its own:
- **classics**: three of its four `.DIY` files are the PC game's binary format, which only the SDL
  build reads (`src/diy_import_dos.c`), and the SWOS 2020 ones come from the assets folder, which an
  Amiga drawer has none of. Its biggest menu (30 KB of JSON) would also take about four seconds to
  build there.
- **hair** and **weather**: they draw pixels, and `ModApi_Frame` is the SDL build's chunky frame
  (a byte a pixel). The Amiga's screen is bitplanes, so a mod that draws needs a drawing API that
  knows them (and `ModApi_PaletteColour` from the copper list) -- its own piece of design. The rain
  draws through the renderer too. The drawer carries
`data_json/menus/openswos/` (the MODES screen's menu: `build_dist.sh`, and the setup's WHDLoad
package).

**Memory:** against the build before it, 54 KB more code and 30 KB more BSS (the loader's scratch
is allocated per menu on the Amiga; its tables are cut down there).

Checked (FS-UAE, A1200, `data/MODS` = practice): MODES on the main menu, its screen, PRACTICE's
menu from the mod's folder, a DEMO GAME (a mod's match, CPU against CPU) played to its end and
back to the practice menu, and TEAM TRAINING's menu; SPEEDRUN's screen and its records saved and read
back; CHALLENGES' list from both mods' folders, HOLD ON's page, and its match kicking off at 70
minutes, Italy 1-0 Brazil. On SDL the mod tests are unchanged
(`SWOS_MOD_MATCH_TEST=1`, `shootout`, `speedrun:0/3`, `SWOS_SHOOTING_TEST`), and so are the golden
careers and `check_netplay_compat.sh`.

## 31. The career's players (src/mod_career.c; Career+'s §3.5)

Ten calls (include/mod_api.h) that go through the game's own career code, so what a mod does
is kept, saved and shown as the game's own transfers are. A team is `file << 8 | ordinal`, a
slot a player's place in the team's file (0-15; 0-31 for your club); each gives -1 outside a
career or when it cannot.

| call | what it does |
|---|---|
| `ModApi_CareerTeam(team, out)` | the club's 16 players as the career has them: its live copy (the current team, your club, the selected teams, the TMD pool), else its file's record with the career's pool on it, as GetTeamPointer gives -- but the team-file buffer a screen may be showing is put back as it was (`Career_PeekTeam`, `TeamFile_PutAside`/`PutBack`: allocated, as the Amiga keeps no second buffer), and an id with no team file gives -1 (LoadTeamFile halts on one, panic 0x8008) |
| `ModApi_SetCareerPlayer(team, slot, player)` | another club's player becomes `player` for the rest of the career: the claim in the career's foreign pool (updated, or one added; -1 when the pool is full, `foreign_pool_capacity`) and every live copy (`Career_WriteTeamPlayer`). Never your club: its players change through the game's transfers |
| `ModApi_OfferForPlayer(team, slot)` | the game's MAKE OFFER screen for that player, with BUY PLAYER's own tests first (time left to negotiate, room in the squad); 1 when the transfer was made. From a `MODPOINT_BUY_PLAYER` / `MODPOINT_TRANSFER_MARKET` entry the screen then closes as it does after the game's own buys |
| `ModApi_CallUpPlayer(team, slot)` | a national selector's pick, from the `MODPOINT_NATIONAL_ADD_PLAYER` entry: refused as the squad screen greys players out (another nationality, already in the squad, unavailable); when the entry returns ADD PLAYER closes and the game adds him as HOME / ABROAD would, a full squad included (`Career_AddInternationalPlayerPicked`) |
| `ModApi_CareerTeamName(team, out, cap)` | the club's name, found as `ModApi_CareerTeam` finds it (a 17-letter name has no NUL in the file; this one has) |
| `ModApi_ViewedCompetition(&id, &league, &division)` | from a `MODPOINT_COMPETITION_STATS` entry: the contest that STATISTICS screen shows -- its id (as `competitionFinished` gives it), whether it is its country's league, and then its division; a cup otherwise (a continental league phase too). Read from `_diyCompetitionStart` as the WINNERS screen reads it (`WorldWinners_Viewed`) |
| `ModApi_CareerClubs(each, ctx)` | every club of the career's countries (those with a league: no national team, no joke teams), each as `ModApi_CareerTeam` would give it -- team id, name, division, line-up order (`playerNumbers`), its 16 -- a team file at a time (`Career_ForEachClub`: read once and copied, so `each` may call the rest; the team-file buffer put back). About 1,500 clubs, about 2 s on a desktop: once a season, not every frame |
| `ModApi_PlayerValue(player)` | his value in thousands, as the transfer screens show another club's player (`_avgTeamValueBases[_avgTeamValues[price]]`) |
| `ModApi_SetOwnPlayer(slot, player)` | your club's player at slot 0-31 (the reserves too) becomes `player`, a new man in his place (Career+'s retirements): the career squad and its live copies, its values marked to be worked out again (`Career_WriteOwnPlayer`). Not a national team's squad |
| `ModApi_ListPlayer(slot)` | your player onto your transfer list: 1 when he is on it already (the game's own add does not check), -1 when the list is full (`transfer_list_capacity`) or the slot is empty |

Both targets: on the Amiga, `Career_PeekTeam` asks resload whether `data/team.NNN` is there
(`Resload_FileSize`) where the SDL build asks the data_json corpus, then the binary file.
