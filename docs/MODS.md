# MODS.md — mods, tweaks, and what stays the base engine

Status: **design agreed 2026-11-04; §8.1's overlay, canonical/DLC mods and their uuids (§14), and the first tweaks are built** (§12), the rest is not. People are forking OpenSWOS to add
what they want, and that is good, but the project cannot merge every fork. A mod system lets
those features exist without being merged, so the engine has to become flexible enough to
host them. This file records the decisions, the survey they came from, and the plan.

---

## 1. Decisions (the owner, 2026-11-04)

1. **The line:** what makes the engine *able to do more* is the **base**; what makes the game
   *different* is a **mod**. There are exceptions (§4, tweaks).
2. **PR #11** (petarku, HISTORIC TOURNAMENTS): the PC/SWOS 2020 `.DIY` reader and the
   competition-load speedup go into the base; HISTORIC TOURNAMENTS becomes the first content mod.
3. **CPU cards** ("the computer gets cards too") goes into the base as a tweak: two forks built
   it independently (petarku, benefactorr).
4. **Code mods** start as source mods compiled in, **with Lua script support at the same time**.
5. **World 2026-27 becomes a mod**, once the overlay and registries exist.
6. **The pitch format is base** (§6): Tile Agent's maps, made with Tile Agent, with a binary
   form the Amiga reads.
7. **Tweaks:** behaviour that differs from the original but is not a mod -- small fixes of the
   original's annoyances -- in `[tweaks]` of SWOS.ini, off by default (§4).
8. **The original is always buildable:** every divergence from the Amiga game sits behind a
   preprocessor switch (§5), and the Amiga gets an **OCS/ECS target** with the original
   graphics beside the AGA one (§7).

We call them **mods**: the word the SWOS scene already uses (the SWOS 96/97 Mod, "modding").
A SWOS 2020 "DLC pack" is a mod you download.

What it shows:

- **No fork is only data, and none is only code.** Each is a few new systems, some content,
  and menu rows.
- **Every fork edits the same places**, the places the engine has no way in: menus (rows in
  FRIENDLY, OPTIONS, PRESET COMPETITION; the Amiga's compiled `menu_data.c`), strings
  (`string_symbols.c` regenerated by nearly every fork), settings (SWOS.ini keys, OPTIONS rows),

  career events (season start and end, the transfer window, AI decisions), and saves.
- **Ports are not mods.** The 3DS and AROS stay forks or come back as targets (as PortMaster did).
- **A deep mode like Indoor stays partly code** even with every hook below; the hooks make
  most of it data and the rest small.

## 3. What is base and what is a mod

**Base:** the original game, faithful to the Amiga and DOS releases (the replay rig and the
golden careers prove it); platforms and infrastructure (ports, netplay, saves, replays, the
setup); reading formats (PC `.DIY`, SWOS 2020's files, Tile Agent maps); the capabilities mods
need (§8); bug fixes and speedups; tweaks (§4).

**Mods:** new modes (indoor, practice, challenges), rule and balance changes, new career
systems (ageing, AI transfers), and content: competitions, worlds, team data, pitches, kits,
graphics, music, commentary, translations.

PR #11 split this way: the `.DIY` reader, the load speedup (petarku offered it as its own PR:
take it first) and the Amiga's folder listing / data-root loading are base; HISTORIC
TOURNAMENTS -- SWOS 2020's cups, which Insane has agreed may be redistributed, with a manifest
-- is the first content mod, shown by a generic "competitions from mods" row in PRESET
COMPETITION so no mod edits `teams.c` or `menu_data.c` again.

## 4. Tweaks: `[tweaks]` in SWOS.ini

A tweak changes how the original behaves where the original annoys: small, self-contained,
**off by default**, one key each. First ones:

| Key | What it does | From |
|---|---|---|
| `cpu_cards` | the computer's players are booked and sent off too | petarku, benefactorr |
| `no_teammate_tackles` | a team-mate does not tackle the player on the ball | a Reddit report |
| `tackle_controlled_player` | a slide tackle is made by the player you control, not another | a Reddit report |

Before any of these is written, **check it against the original** (`data/SWOS2.s`, and
`swos.asm` for DOS): a report is not automatically right. If the original does it, it is a
tweak; if only OpenSWOS does it, it is a bug and is fixed in the base for everyone.

A tweak that changes a match is **match rules online**: it travels in the host's rules like the
lobby's switches (SHORT PRESSES, CARDS/INJURIES: `include/netplay_match.h`), the joiner plays
the host's, the recorder and `.SRP` record it, and adding one raises `NETPLAY_COMPAT`. The
golden careers and the replay corpus run with every tweak off, so they keep proving the original.

## 5. The original, always buildable

Every behaviour that differs from the Amiga game -- tweaks, mods, the worlds, gameplay styles
the original never had -- is compiled in only under a switch, so one flag builds the original:

- `SWOS_ORIGINAL=1` (both makefiles): no tweaks, no mod loader, no worlds (`SWOS_WORLDS=0`, which
  exists), only the AMIGA and DOS gameplay styles. Additions that do not change how the game
  plays (widescreen, netplay, the setup) are not divergences and stay.
- New divergent code is written behind its switch from the start (as `SWOS_WORLDS` code is:
  CLAUDE.md, "new world code must keep that true").

## 6. Pitches: Tile Agent's format, in the base

The pitch becomes a Tile Agent map: layers, some above the players, and animations with easing
(`docs/PITCH_FORMAT_V2.md`; the format is Tile Agent's own, `D:\Projects\GitHub\TileAgent`
`docs/FORMAT.md`). Stage 1 is in the game: a DOS-graphics pitch drawn from a `.tmj`
(`docs/PITCH_MAPS.md`, `[graphics] pitch_maps`). It is base, not a mod, because it is a format
the engine reads; the pitches made with it are mods.

- **SDL** reads the `.tmj` and its images directly (the runtime in `third_party/tileagent`).
- **The Amiga reads a binary**, never JSON (parsing JSON on a 68k takes seconds per file):
  `.PCH`, the layout in PITCH_FORMAT_V2.md §6 -- tile indices not offsets, big-endian, a magic,
  a version and a **capability word**. It takes the base layers and the crowd's animation and
  refuses a pitch that needs more (over-sprite layers, alpha, many animations) cleanly. Chip RAM
  has ~4 KB headroom beyond the 82 KB pitch buffer, so a pitch must fit what the game has.
- **Who writes the binary:** one C writer, in the Tile Agent runtime, used by **both** Tile
  Agent's export and OpenSWOS Setup. An author exports `.PCH` from Tile Agent; a mod that ships
  only the `.tmj` gets its `.PCH` made by the setup when it builds an Amiga drawer. One writer,
  so the two never disagree.
- Next stages (PITCH_MAPS.md, "what the map could take over next"): the crowd's behaviour, the
  adverts, the flags and goals from the map instead of the engine's code; then the AGA and OCS
  tiers' pitches as maps too.

## 7. The Amiga OCS/ECS target

The original's graphics on the original's chipset, as its own build beside the AGA one:
`make -f Makefile.amiga OCS=1` -> `bin/SWOS2_OCS`, the 4-bitplane `grafs/` tier, without
`#define AGA` (`include/display.h`: the switch exists, last verified before the recent AGA work,
docs/AGA.md). Its own SWOS drawer in the setup. To measure first: the binary's size and what it
needs of chip and fast RAM -- the AGA build needs 8 MB of fast; an A500 or A600 with an
expansion, or an emulator set up as one, is the likely floor, and the doc will say so.

## 8. What the engine needs (the order to build it)

1. **The overlay and the manifest.** A mod is a folder with `mod.json`: id, name, version,
   author, targets (`sdl`, `amiga`, both), what it changes (`cosmetic`, `gameplay`, `career`),
   its files per target, and for the Amiga the sizes it needs. `swos_data_path()` on SDL and the
   resload file calls on the Amiga look through each enabled mod, in order, before the base data.
   The enabled list: `[mods]` in SWOS.ini, `data/MODS` in an Amiga drawer. On the Amiga a mod
   replaces a file, not memory: files already load on demand into their own buffers.
2. **Registries instead of edits.** A mod adds menus and rows at named insertion points, strings
   with their translations, and settings with their OPTIONS rows. On the Amiga a mod ships its
   menus already packed (the binary the JSON loader makes today), never as JSON.
3. **The ruleset.** One structure the match reads instead of constants: players per side, the
   pitch's size and walls, match length, card and substitution rules, physics parameters, the
   tactics set. Much of Indoor becomes a ruleset plus art; what is left becomes generic features
   in the base (walls, time penalties).
4. **Match setup.** Who plays, the starting state, how it ends, how it is scored: shooting
   practice, penalties and challenges become data.
5. **Career events and saves.** Season start and end, the transfer window, AI decisions, as
   hooks; each mod a named section of the JSON save (named fields, never addresses: CLAUDE.md).
6. **The online contract.** A `gameplay` mod's id, version and hash go in the handshake, and two
   builds whose gameplay mods differ do not start a match (like a different `NETPLAY_COMPAT`).
   `cosmetic` mods may differ. **The goal (the owner, 2026-11-04): mods in multiplayer** -- two
   players with the same gameplay mods, at the same versions, play each other; the matchmaker
   lists a game only to players whose gameplay mods match (as it does by `NETPLAY_COMPAT`), and
   the lobby says which mod is missing or differs. Until then a gameplay mod keeps the game off
   line (§12). Tweaks travel the same way, in the host's rules (§4). Recordings carry the mod
   list, so a replay and `--srp-resim` play by it. A gameplay mod's match state registers with the rollback registry (`src/sim_state.c`).

## 9. Code mods

**Source mods first.** `mods/<id>/` with its sources and `mod.json`, built into the binary
(like `fork.mk`), enabled or not at run time from the list in §8.1. They work on every target,
the Amiga, iOS and the web included, and stay deterministic. They call the hooks of §8; they
never patch the engine's code. They are how the hooks get tried on real cases: Indoor and
Career+ are the first two to port.

**Lua at the same time.** Lua 5.4 (MIT: fine beside GPL-3.0-or-later), embedded, calling the
same hooks as the source mods -- a script can do what a source mod can, through one API.

- Runs on every SDL target (desktops, phones, the web, handhelds).
- Numbers are **integers** for anything a match or career sees (a `luaconf.h` with 32-bit
  integers): floats differ across machines and the Amiga has no FPU, and both peers of a match
  must compute the same.
- The Amiga builds `-nostdlib`, so Lua there needs the small libc it uses (allocation over the
  game's heap, strings, `setjmp`); a 68020 is fast enough for menus and season events, **not**
  for anything run per player per frame. A mod says whether its scripts are needed on the Amiga.
- Scripts are sandboxed: no files outside the mod's folder, no network, no OS.

Native modules (`.so`/`.dll`, an Amiga LoadSeg module) are not planned: per-target, impossible
on iOS and the web, and broken by every engine change.

## 10. Distribution

One manifest format and one index for every mod manager: OpenSWOS Setup on a PC or Mac, SWOS
Launcher's DLC Manager on the Amiga (over Roadshow), the phone copy. An index entry says which
targets a mod is for -- which also gives SWOS United and SWOS United Amiga their own downloads.
Mods are hosted by their authors (content with other people's rights stays theirs, as World
2026-27 is Davide's); the index only points to them, with each file's hash.

## 12. Built so far

**The overlay (§8.1), both targets** (`include/mods.h`, `src/mods.c`):

- **SDL:** `[mods] enabled = a, b` in SWOS.ini (or `--mods=a,b`, or `SWOS_MODS_ENABLED` for one
  run). Mods are folders in `mods/` in the player's game folder (`$SWOS_MODS` elsewhere), each
  with a `mod.json`; one whose `targets` lacks `"sdl"`, or with no folder or manifest, is left
  out and the log says why (`[mods]` lines). `swos_data_path()` looks in each mod, in order,
  before the assets folder and the game's own files; `swos_data_path_base()` (saves, deletes)
  never does. Mods start before translations load, so a mod can carry its own.
- **Amiga:** the drawer's `data/MODS`, one id a line (an id ending in `*` is not cosmetic),
  read at the first file read; `make_read_path()` in `src/resload.c` looks in
  `PROGDIR:mods/<id>/` (or `mods/<id>/` under WHDLoad) for every load, never for a save.
- **Online:** a mod whose `changes` is not `"cosmetic"` (or says nothing) keeps MULTIPLAYER
  off ("TO PLAY ONLINE, TURN OFF THE MOD ..."), until §8.6.
- **Checked:** SDL -- a test mod's `en.json` renamed an OPTIONS row (screenshots with and
  without), MULTIPLAYER refused with a gameplay mod; Amiga (FS-UAE) -- a test mod's
  `grafs_aga/MENUBG.RAW` replaced the main menu's backdrop (screenshots with and without);
  `--menu-selftest` and `scripts/replay_v2_test.sh --all` unchanged with no mod.
- **Not yet:** OpenSWOS Setup installing mods and writing `data/MODS`; a mods screen in the game.

**The first tweaks (§4)** (`include/tweaks.h`, `src/tweaks.c`): `[tweaks]` in SWOS.ini, each
`true | false`, off by default; off online and under every rig (`Tweaks_On`); the Amiga has none.

| Key | The original (checked: SWOS2.s and swos.asm agree; our C matched) | The tweak |
|---|---|---|
| `cpu_cards` | `TryBookingThePlayer` / `TrySendingOffThePlayer` give no card to a side with no human (SWOS2.s:26026) | `src/tackle_foul.c`: every side by the same rolls |
| `tackle_controlled_player` | whichever of the controlled player and the pass receiver is nearer the ball slides (SWOS2.s:30408-30431 and 31116-31146) | `src/update_players.c`: on a human's team only the controlled player slides |
| `no_teammate_tackles` | the receiver runs onto the ball (`passingBall`), may slide on your fire press and is handed control on reaching it (SWOS2.s:31146-31215) | while a human's controlled player has the ball (within 72), the receiver comes to support distance only: no slide, no hand-over |

Checked: with every tweak off, `rollback_test.sh --all`, `replay_v2_test.sh --all` and
`netplay_test.sh --all` pass; both targets build. **Not yet played with the tweaks on.**

## 13. SWOS United: a thin fork plus a mod (agreed 2026-11-04)

SWOS United (github.com/SWOS-United/SWOS-United) is three things, and only two are a mod:

| Part | Where it goes |
|---|---|
| SWOS 2020's online look: MATCH MAKING, RANKINGS, LEAGUES, the lobby, CHOOSE GAMEPLAY's icons | **the United mod** -- menus and their handlers, through the registries (§8.2) |
| accounts and its own servers: SWOS-API log-in, swos.swosunited.com's rankings and leagues, its matchmaker | **the United mod**, as a source mod (it talks to the network and handles log-ins: not a sandboxed script), through a new **online-provider hook**: which server, how to log in, where rankings and leagues come from |
| its identity: name, icon, phone app ids (`com.swosunited.game`), installer, player folder, netplay tag | **stays the fork**: `include/project_identity.h`, its packaging and icons. A mod cannot rename an app or give it an installer |

The aim is a **thin fork**: `project_identity.h`, packaging, icons and the mod -- no shared file
edited, so a merge of OpenSWOS never conflicts. (The merge of 2026-11-04 had five.)

**Order:** after the registries (§8.2) and the online contract (§8.6). The online-provider hook
is designed with United as its first user, and **with United's team**: it changes how they work.
It is also the hook any fork uses for its own online service (FORKING.md: a fork runs its own
server).

**Syncing United while it moves -- the care it needs:**

- **Until the hook exists, United stays a full fork** and merges OpenSWOS as today
  (`git merge upstream/main`, never rebase; FORKING.md). Its online code is where conflicts
  come from (`src/online_menus.c`, `src/platform_sdl.c`, `include/project_identity.h`).
- **Move United's code into its mod one piece at a time**, each piece in its own United commit:
  a screen goes into `mods/united/` as soon as the registry it needs exists in OpenSWOS, and its
  edits to the shared file are removed in the same commit. Never half-move a screen.
- **Each sync, after the merge:** build both targets; `--menu-selftest`; check the identity
  header kept United's values (app id, tag, servers) and that player-facing paths name
  `com.swosunited.game` (the Android folder in INSTALL.md and the install page); and log in
  and play a match through United's own server, which OpenSWOS's tests never reach.
- **Shared decisions stay explicit:** where OpenSWOS and United both have a feature (XBOX in
  CHOOSE GAMEPLAY, 2026-11-04), the merge keeps OpenSWOS's in OpenSWOS's look and United's in
  its own; a conflict there is resolved by asking, not by picking a side.
- **OpenSWOS never merges United** (FORKING.md); a United fix OpenSWOS wants is cherry-picked.

## 14. Canonical mods and DLC mods; every mod a UUID (the owner, 2026-11-04)

Some of SWOS 2020's features become mods, so mods come in two kinds:

| | **Canonical** | **DLC** |
|---|---|---|
| What | part of OpenSWOS: maintained in the repo, shipped in every drop, tested with each release | downloaded: by its author, or the project's, hosted outside the game |
| Where | the game's own `mods/` (`MODS_CANONICAL_DIR`; `bin/mods/`, git-tracked) | the player's `mods/` folder (`Mods_Root()`), put there by OpenSWOS Setup or the Amiga DLC Manager |
| Rights | only what OpenSWOS may ship | anything its author may share. **Content with other people's rights is always DLC**: World 2026-27, SWOS 2020's cups (HISTORIC TOURNAMENTS' data), the SWOS 2020 pitches. The engine capability that reads it can be canonical (the `.DIY` reader is base) |
| On | when its manifest says `"default": true`, unless `[mods] disabled` names it; or when `[mods] enabled` does | only when `[mods] enabled` names it |
| Online | part of the build: the same build has the same canonical mods (`NETPLAY_COMPAT`), so never a blocker | matched by uuid, version and hash (§8.6); until then a non-cosmetic one keeps the game off line |

**Every mod has a `uuid`** in its `mod.json`, separate from its folder's name (the slug, a
readable label that may change). The uuid is the identity in saves (a career made with a career
mod records its uuid and version), the handshake, recordings, the index, and dependencies.

- **Canonical:** `uuid5(NAMESPACE, "mod/<slug>")`, NAMESPACE being the project's
  (`af19cc5a-6529-537b-935b-407bd73b75fb`, scripts/assign_team_uuids.py), written into the
  manifest once and never changed:
  `python3 -c "import uuid;print(uuid.uuid5(uuid.UUID('af19cc5a-6529-537b-935b-407bd73b75fb'),'mod/<slug>'))"`
- **DLC:** a random uuid4, made by its author when the mod is made.
- **Refused** (the log says which): a mod with no uuid; a second mod with a uuid already on; a
  DLC with a canonical mod's uuid. The Amiga reads no manifest, so it trusts the setup's
  `data/MODS`, which the setup writes from manifests it has checked.

**Order:** the `[mods] enabled` list first, in its order (a slug that is a DLC folder is that DLC,
else the canonical mod of that slug), then the canonical mods on by default. A file two mods
have comes from the first.

When the first canonical mod lands, add `mods` to the trees every drop stages
(`build_dist.sh` FULL_DATA_DIRS, `build_installer.sh` DATA_DIRS, `make macos-app`,
`packaging/mobile/CMakeLists.txt`, `build_portmaster.sh`, the Amiga drawer), as the other
tracked `bin/` trees are.

Checked (SDL): a DLC with no uuid refused; a DLC with one on; a DLC with a canonical uuid
refused; a canonical mod on by default and off with `disabled`. Both targets build.

## 15. Registries (§8.2): what exists, what is built, what comes next

**What a mod can already do on SDL, through the overlay alone** (found 2026-11-04):

- **Replace any menu.** The original's 47 menus are rebuilt from `data_json/menus/*.json` at
  every start (`MenuJson_InstallAll`, on by default), and those reads go through the overlay;
  the SWOS 2020 and OpenSWOS menus load from JSON when first shown. Limit: an original menu may
  not grow past its compiled size (it is written over the compiled bytes; a bigger one is
  skipped and logged) -- growing one needs MENUS.md §1e's call-site repoint.
- **Replace formations** (`data_json/tactics`, on by default) and the career parameters
  (`career_params.json`).

**Built: strings** (`src/translations.c`). A mod's `data_json/translations/<lang>.json` holds
only the strings it adds or changes, and is **merged** over the game's: each key it has
replaces the game's or joins the table, the first mod in the list winning a key two mods have.
The game's own file is read without the overlay, so a mod never replaces the whole table.
Checked: two mods each renaming an OPTIONS row and both renaming a third -- both renames shown,
the first mod's winning the shared one.

**Next, in order:**

1. **A MODS screen** (OPTIONS -> MODS) -- **built** (`src/mods_menu.c`,
   `openswos/modsMenu.json`): every mod on disk (`Mods_Scan`), canonical then DLC, up to 8 rows
   of name, version and kind with ON / OFF / CANNOT (a mod that cannot be on: fire says why);
   fire turns one on or off, written to SWOS.ini at once, played from the next start. OPTIONS'
   value says how many are on; hidden on the Amiga (its list is data/MODS). Checked: the screen
   with a canonical, a DLC and a broken mod; toggling both kinds wrote `enabled=hall`,
   `disabled=classics` and the next start played by it; `--menu-selftest` covers it. Still to
   come: each mod's own page (its settings, item 2), more than 8 mods. Mods add to the game **there, and at named hooks**, rather than by
   squeezing rows into the original's screens -- those keep their layout, so `SWOS_ORIGINAL`
   stays the original and two mods never fight over one row.
2. **Mod settings.** `mod.json` `"settings": [{ "key", "label", "choices": [...], "default" }]`,
   kept in SWOS.ini `[mod.<slug>]`, shown on the mod's page, read by its code
   (`Mods_Setting(uuid, key)`).
3. **Named hooks** where a mod's content appears in the game: "competitions from mods" in
   PRESET COMPETITION (HISTORIC TOURNAMENTS is its first user), then modes (FRIENDLY, the main
   menu) as mods need them -- each a generic entry the engine draws from what mods register.
4. **Handlers.** A data-only mod's menus use the handlers the game already has (the menu
   symbol registry, `_menuSymbols`); a code mod (§9) registers its own as `<slug>.<name>`.
5. **The Amiga** has no menu symbol registry (`menu_symbols.c` is SDL-only) and no run-time
   translations. Its mod menus will be packed binary (scripts/menu_json_to_bin.py, MENUS.md
   §3) whose references are indices into a compact Amiga registry; measure its size first.
